# CookAssistance — execution loop

Целевой продукт — Android-приложение. Стек и UI-требования: [ANDROID.md](ANDROID.md). Этот файл определяет координацию, объём проверки и условия завершения. Разделы ниже «Размер задач», «Проверки без повторных полных прогонов» и «Эмуляторы» имеют приоритет над прежними указаниями профилей запускать всю матрицу после каждого изменения. Это изменение порядка работы, а не разрешение скрывать ошибки или ослаблять критерии.

## Переносимость между харнессами

Харнесс — среда запуска агента: CLI, IDE, desktop или иной клиент. Эти правила не требуют конкретного поставщика, названий инструментов, MCP или интеграции с трекером. Приоритет: обязательные ограничения среды и явные требования пользователя, затем этот файл, затем профили. Правила переносимости, последовательного исполнения и локального учёта ниже применяются ко всем профилям и связанным документам проекта.

Если харнесс не загружает `AGENTS.md` автоматически, явно прочитай его и выбранный профиль перед работой. Используй доступные штатные инструменты: файловые операции, shell/Git CLI, API или средства автоматизации. Имена и схемы инструментов проверяй в текущей среде; примеры вызовов в профилях не являются гарантией их наличия. Пути разрешай от фактического repo_root; команды адаптируй к ОС и shell. Для Gradle используй wrapper проекта (`gradlew.bat` на Windows, `./gradlew` на Unix).

На preflight сохрани capabilities: ОС/shell, доступ к файлам и командам, выделенный checkout, Android SDK/эмулятор/UI-автоматизацию и доступ к Git-хостингу в пределах scope. Субагенты и слоты не требуются. Отсутствие необязательной интеграции не блокирует работу. Для недоступной обязательной проверки или публикации сохрани конкретный BLOCKED; не выдумывай вызовы и результаты.

Все профили выполняет текущий агент последовательно. Для перехода прочитай соответствующий файл profiles/*.md, выполни его инструкции, сохрани результат/checkpoint и вернись к исходному этапу либо продолжи цикл. Не создавай субагентов, отдельных консультантов или пользовательские чаты. Product и tech — этапы принятия решений тем же агентом. Review — отдельный проход самопроверки с review_mode=self; внешний reviewer для локальной готовности не требуется. Обязательный человеческий review хостинга сохраняется как gate публикации.

Для небольшой правки документации или инструкций достаточно согласованного scope: чтение затронутых файлов, проверка diff, ссылок и противоречий. Android preflight/build/smoke и публикация не запускаются без связи с изменением или явного требования. Это исключение действует во всех профилях: для документации Android-этапы помечай NOT APPLICABLE с причиной, не BLOCKED. Коммит и доставка выполняются только в согласованном scope. Для локальной правки допускается снимок кандидата вместо коммита. Это не разрешает менять код приложения без его проверок.

## Переходы и границы профилей

Переход к профилю — внутренний этап текущей задачи. Сохрани return_profile/return_phase и причину перехода. При консультации выполняй только анализ/решение, затем вернись; не запускай вложенный execution loop. При повторном входе в уже активную консультацию используй сохранённый вопрос и решение либо зафиксируй BLOCKED, не создавая рекурсивный переход. Изменение общего контракта оценивай через product в режиме consultation.

При прямом запросе отдельного профиля исполни его scope и верни результат; не переходи автоматически к реализации, публикации или развитию вне запроса. Внутри product-loop завершение этапа возвращает управление сохранённому этапу. APPROVE/PASS/FAIL/BLOCKED — результаты этапов, а не требование завершать весь пользовательский ответ после каждого перехода.

Для незакоммиченного кандидата фиксируй base HEAD, staged/unstaged diff и манифест всех новых файлов в scope с SHA-256 их содержимого. Отдельно отмечай существующие чужие изменения. Один git diff не включает untracked-файлы; review должен читать их содержимое. Любое изменение включённых файлов меняет снимок и требует проверки затронутой дельты. Android APK перед публикацией связывай с коммитом кандидата по правилам provenance.

Основную ветку определяй фактически по конфигурации Git/remote. Ниже main означает эту ветку, даже если она называется иначе; при неоднозначности сохрани blocker интеграции, не переименовывай ветки автоматически.

Worktree может содержать старую копию инструкций: сверяй её до использования; актуальные правила применяй явно, чужие незавершённые изменения автоматически не коммить. Текущая policy revision: `2026-11-11-gateway-bootstrap-5`.

## Решения и подготовка

Все вопросы решает `/product`, техническую оценку даёт `/tech`. Пользователю не отправлять вопросы о реализации, приоритетах или следующем этапе. Явные требования пользователя обязательны; недостающее определяй самостоятельно, записывая допущения в `workflow/decisions.md`. Не выдумывай авторизацию, секреты, владельца аккаунта или результаты проверок и не обходи ограничения среды. Недоступный сервис: доступная альтернатива либо конкретный blocker и независимая работа. Обязательные запросы разрешений самой среды не отменяются профилем.

Preflight один раз на запуск в пределах scope: фактические repo_root/HEAD/ветка/status, актуальный remote и capabilities харнесса; для Android-задач также JDK/SDK/Gradle, AVD/API/ABI и UI-инструменты. При resume сверяй изменения, не исследуй заново уже подтверждённую среду. Если проекта ещё нет, bootstrap отдельной задачей; не смешивай его со всем MVP. Используй существующие Git и локальный реестр задач, не пересоздавай их. Для явно нового проекта допустим git init в его рабочей папке.

Для отсутствующего remote сначала ищи однозначно соответствующий репозиторий в авторизованном подключении. При отсутствии допускается создание приватного репозитория в однозначно установленном личном аккаунте доступным инструментом; без платы, публичной видимости и вмешательства в чужие проекты. Если нет доступа или владелец неоднозначен — publication blocker без вопроса пользователю. Подготовка JDK/SDK/AVD выполняется штатно в пределах доступа, по возможности настройками проекта/процесса.

## Размер задач и очередь

1. До основной реализации разложи ТЗ на карточки с самостоятельным проверяемым результатом, зависимостями и 2–5 критериями приёмки. Не помещай bootstrap, каталог, избранное, backend/AI и голос в одну feature-карточку. Общее MVP — epic, не единица исполнения.
2. Для помощника по готовке подходящее разделение: Compose bootstrap; каталог; детали рецепта; offline-избранное; контракт backend; подключение DeepSeek; голосовой ввод; озвучка. Разделение определяется связностью, не желаемым количеством карточек. Уже написанный монолитный MVP разделяй по фактической готовности в состоянии/доске, не переписывай код только ради новой структуры задач.
3. До начала каждой карточки выбери минимальную полезную вертикальную реализацию, impacted modules и конечный набор проверок. Если план затрагивает более двух независимых пользовательских сценариев или одновременно новый backend и несколько Android-фич, сначала раздели задачу. Не задавай обещание завершить её за фиксированное время.
4. Отсутствующий DeepSeek key блокирует живую AI-приёмку, а не каталог и избранное. Remote блокирует публикацию, а не локальную готовность. Mock/typed input не засчитываются за live AI/реальный голос. Не перепроверяй неизменившийся внешний blocker при каждом smoke.
5. Статусы разработки и доставки раздельны: `Planning → In Progress → Review → Validation → Locally Ready`; отдельно `Publish Blocked / Ready to Publish → Published/Ready to Merge → Done`. Локально готовую карточку не переделывай из-за отсутствующего remote. Общий MVP не Done, пока обязательные критерии заблокированы.
6. Карточки выполняй последовательно, WIP=1; при внешней блокировке сохрани checkpoint и выбери доступную независимую задачу. Зависимые задачи могут основываться на уже проверенной неопубликованной ветке с явным base SHA и зависимостью. В финальную публикацию включается проверенная цепочка. Непроверенный код не становится базой молча.
7. Каждая самостоятельная фича и каждый воспроизводимый баг получают отдельную карточку. Повтор одного дефекта обновляет существующую карточку; общая причина нескольких симптомов может быть одним багом. Неблокирующие находки идут в очередь, блокирующий дефект связывается с родителем. Не расширяй текущую реализацию побочными фичами.
8. WIP разработки — одна карточка, профили выполняются последовательно. Зависимости и конфликты оценивай на этапе product; подробный цикл — в profiles/product.md. Смежные функции развивай после обязательного доступного функционала и только в разрешённом режиме. Отсутствие данных не компенсируй придумыванием задач; количество карточек не метрика качества.

## Короткий цикл задачи

`bootstrap gateway → product → planer → dev/bugfix + ранняя подготовка unit/smoke-сценариев → интеграция тестов → review → проверки кандидата → security review через Gateway → commit → Locally Ready → публикация/интеграция`.

Подготовку критериев и smoke-сценариев начинай при готовом плане. Unit-тесты добавляй вместе с кодом, а не обязательно после первого APPROVE. `/unit-test` и `/smoke_scenario` проверяют/дополняют назначенные файлы до финального ревью; роли сохраняются, бессмысленный второй цикл review только из-за поздно начатых тестов не требуется. Если дополнительный тест всё же изменил кандидат, его diff требует ревью.

Проход /review обязателен и выполняется текущим агентом отдельно от реализации без редактирования кода в ходе проверки. Это самопроверка: сохраняй review_mode=self, не называй её независимым внешним review. На первом проходе читай весь diff задачи, на повторном — замечания и новую дельту с проверкой контекста/интеграции. Успешный результат этапа — APPROVE; свяжи его с SHA или полным снимком незакоммиченного кандидата. При прямом запросе /review финальный ответ без замечаний ровно APPROVE; внутри цикла сохрани результат и продолжи следующий этап. Изменение кандидата требует подтверждения review. Отсутствие отдельного reviewer локальную готовность не блокирует; требования внешнего review для merge сохраняются.

## Security gate и LLM Gateway

Первый шаг запуска — [bootstrap gateway](docs/gateway-bootstrap.md), до приватного
контекста и любых LLM-вызовов. Если установки нет, проверенный оператором bootstrap
запускает одноразовую настройку с подтверждением повышенных прав; только после
проверки готовности под ограниченной учётной записью начинается loop. На следующих
запусках используется установленный защищённый bootstrap: только проверка готовности,
без изменения файлов/прав/seal. Повреждённая или частичная установка — BLOCKED,
не автоматический repair. Агент не получает постоянных административных прав.

Обязательна [защищённая установка runtime](docs/runtime-integrity.md): другой
владелец, отсутствие у агента прав записи/замены/смены ACL, проверка seal до
импорта, изолированный Python launcher. Не меняйте gateway, policy, security-
промпт, эталонные hashes или права ради прохождения проверки. Обновление runtime
выполняет оператор отдельно после review; агент не пересобирает seal при BLOCKED.
Если агент может менять защиту или запускать её с административными правами,
production-запуск блокируется. Контроль целостности в памяти не заменяет права ОС.

Обязателен [контракт подключения харнесса](docs/harness-contract.md). До передачи
приватных файлов/результатов инструментов внешней модели подтвердите перехват всех
реальных исходящих каналов и выполните поведенческий preflight коннектора с локальным
приёмником. Текст инструкции, успешный отдельный CLI или флаг enabled не доказывают
защиту внутренних запросов харнесса. Нет коннектора/покрытия — BLOCKED для приватной
работы; не читайте приватные файлы в контекст внешнего агента для настройки защиты.

Security review использует тот же backend/model/config, что генерация, но отдельный
запрос с новым контекстом и security-промптом по [настройке](docs/model-security-review.md).
История генерации, task, предыдущие ответы и feedback в review не переносятся;
передаются только разрешённый снимок и нужные зависимости. Адаптер обязан быть
stateless и не добавлять скрытую историю. Отдельный DeepSeek/ключ не требуется.
Новые реальные export разрешает локальный оператор, не сам агент. CLI требует
установленный commit hook и выполняет preflight заново. Нативные коннекторы не
считаются поставленными, пока не реализованы и не проверены. Встраивающий Python-
координатор соблюдает те же gates явно.

Перед всеми LLM-вызовами execution loop (планирование, генерация, исправление, review, security review, суммаризация и повторные попытки) данные должны пройти локальный LLM Gateway по [контракту](docs/llm-gateway.md). В исполняемом loop Gateway встроен как обязательный локальный этап координатора: отдельный сервис, адрес и токен не требуются. Он отвечает только за допуск и обезличивание контекста, не выбирает модель и не реализует её API. Модель вызывает отдельный доверенный адаптер после успешного допуска; передача исходного/неодобренного контекста или fallback в обход проверки запрещены. Текст инструкции сам не перенастраивает харнесс. Если нельзя подтвердить локальный gate перед его внутренними вызовами, сохранить BLOCKED и не заявлять прохождение Gateway.

После PASS всех назначенных тестов и проверок заморозь полный снимок кандидата и выполни [security review](profiles/security.md) отдельным LLM-запросом с [Android security-промптом](docs/security-review-prompt.md). Это второй запрос относительно генерации, с новым контекстом, а не продолжение самопроверки /review; другой агент/чат не нужен. Обычный review_mode=self сохраняется отдельно.

- Critical/High: FAIL, commit запрещён. Верни структурированный безопасный feedback в dev/bugfix (например: «исправь: SQL injection в RecipeDao.kt, строка 42»); исправь, повтори затронутые тесты, обычный review и отдельный security-запрос для нового снимка. После трёх безрезультатных циклов — product/replan, не обход gate.
- Только Medium/Low: PASS_WITH_WARNINGS; запиши безопасные warning и находки в очередь. Security gate разрешает commit при остальных пройденных gates.
- Нет находок и полное покрытие: PASS; разрешён commit проверенного снимка при остальных пройденных gates.
- Недоступность Gateway/LLM, неполный контекст, невалидный ответ, неизвестная severity или ошибка фильтрации/аудита: BLOCKED, commit запрещён. Отсутствие ответа не означает отсутствие находок.

До gate используй незакоммиченный снимок для кода и документации. Нельзя создавать промежуточный commit/amend с непроверенными изменениями. После gate проверь неизменность staged tree, untracked-манифеста и build inputs, затем коммить только проверенный scope. Любое изменение содержимого кандидата инвалидирует security approval. Для Android после commit свяжи APK с source SHA и неизменными build inputs по правилам provenance; при изменении входов пересобери и перепроверь затронутое.

Исключение для документации освобождает от Android-проверок, но не от Gateway и security gate перед commit. Пока Gateway заблокирован, допустима локальная подготовка инструкций и checkpoint; она не считается выполненным live security review или Locally Ready полного задания.

## Проверки без повторных полных прогонов

В плане фиксируй `validation_scope`: `task`, `fix` или `milestone`, список сценариев/конфигураций и причину выбора. Не расширяй матрицу во время прогона без нового дефекта/требования и решения product. Не сужай её ради зелёного результата.

- `task`: build/lint/unit затронутых модулей, предусмотренные instrumentation; Android UI-проверка основного пользовательского пути новой фичи, её ошибок и затронутой адаптивности. Это локальная готовность карточки, не приёмка всего приложения.
- `fix`: воспроизведение конкретного бага, один убедительный baseline FAIL (если уже есть точный crash/UI evidence, не создавать ещё один стенд только ради повторного FAIL), тот же regression PASS и затронутые смежные сценарии. API-специфический баг проверяется на проблемной и одной контрольной API. Не запускай весь реестр одновременно в fix-worktree и затем снова в parent.
- `milestone`: полный реестр доступных обязательных сценариев и согласованная матрица выполняются один раз на интегрированном, замороженном кандидате перед публикацией этапа/цепочки. Независимая маленькая задача может быть своим milestone. Недоступные обязательные live-критерии остаются BLOCKED, а не PASS.

Unit/lint выполняй инкрементально штатным Gradle, без clean и повторного скачивания среды без доказанной причины. Дешёвые unit/lint не заменяют UI. Release-сборка обязательна на этапе публикации и после изменений build/manifest/DI/serialization/R8; не повторять её на каждой правке текста сценария, если входы сборки не менялись.

Не делай декартово произведение всех экранов × API × тем × размеров × шрифтов. Основной сценарий — на базовой конфигурации; адаптивность — на representative compact/expanded, landscape+IME+200% и теме, затронутых задачей. Полное сочетание требуется, если это явный критерий или воспроизводимый риск. Каждый обязательный критерий должен иметь назначенную проверку; покрытие фиксируется таблицей, не подразумевается.

При первом подтверждённом блокирующем FAIL создай/обнови bug и быстро передай устройство исправлению. Независимые оставшиеся проверки допускаются только в согласованном диагностическом окне до 5 минут; затем сохранить NOT RUN и освободить AVD. Не заставлять fix ждать завершения всей заведомо непринимаемой матрицы. Обязательные незавершённые проверки остаются в финальном плане.

После фикса сначала regression/затронутые проверки, затем оставшиеся элементы финального плана. Не начинать всё с S01 автоматически. Перенос результата допустим только с доказательством неизменности его входов:

- тот же SHA и APK hash, сценарий, конфигурация и backend/test data — использовать уже выполненный результат, не повторять после fast-forward;
- новый SHA, но только docs/tests: явно сопоставить production tree/build inputs, сценарий, APK и среду. Записать `REUSED_FROM` с исходным SHA и обоснованием, не утверждать «выполнено на новом SHA»;
- изменён production-код/manifest/зависимости/сценарий/окружение: затронутые результаты недействительны, повторить их. Финальная совокупность доказательств должна покрывать весь утверждённый план; при сомнении считать проверку затронутой.

Повтор полной матрицы разрешён при изменении общего поведения/архитектуры, неизвестной области влияния или отсутствии надёжных доказательств. Причину записать. Любой баг, даже небольшой, должен оставаться блокирующим для затронутого критерия до проверки исправления.

## Эмуляторы и ресурсы исполнения

Smoke реально запускает AVD/ставит APK и проверяет UI по профилю smoke. Используй доступный Android UI-драйвер: MCP, Appium, UI Automator либо эквивалент с адресацией устройства, действиями и наблюдением экранов. ADB допустим для подготовки и управления; UI-проверка через него требует фактических UI-деревьев/снимков и проверки expected/actual. Одни shell-команды, unit или Python-тесты без взаимодействия с Android UI не являются smoke. До прогона зафиксируй выбранный драйвер и покрытие сценариев; при отсутствии нужной возможности критерий BLOCKED. APK provenance: source SHA, build inputs/variant, APK SHA-256, applicationId, AVD/API/serial; состояние тестовых данных и backend также часть доказательства.

У Android UI-сеанса и глобальных настроек (active device, тема, поворот, font scale) один владелец. Адресуй действия выбранному serial и проверяй изоляцию драйвера; наличие двух serial не доказывает её. Android-прогоны выполняй последовательно, сторонний процесс или занятое устройство не перенастраивай.

Один агент последовательно владеет этапами и Android UI-сеансом. Instrumentation и smoke на одном устройстве не совмещай; не меняй устройство стороннего живого процесса. Для каждой feature/fix используй отдельную ветку и фиксированную базу. Worktree необязателен: допустим выделенный checkout с последовательным переключением после checkpoint. Для правки инструкций в уже изменённом рабочем дереве сохраняй существующие изменения и фиксируй свой scope без обязательного переноса в новую ветку.

До смены профиля сохрани candidate SHA/снимок diff, результаты, pending patches и resume_phase. На новом этапе используй эти данные; не создавай повторную ветку или реализацию. Общие контракты и зависимости фиксируй до разработки, интеграцию веток выполняй последовательно на этапе product. Чужой checkout не переключай.

Передача устройства: сохранить evidence/настройки, освободить lease, немедленно сообщить serial и состояние. Оформление длинного отчёта не удерживает AVD. Сохраняй события автоматически по мере теста, в итоговом отчёте — сводка, ссылки и незакрытые критерии, не повторная ручная перепись всех вызовов драйвера.

## Время и защита от зацикливания

На каждом переходе сохраняй `phase_started_at`, `last_progress_at`, attempts, последний проверяемый результат и следующий шаг. Каждые 15 минут без нового артефакта/диагноза/закрытого сценария product обязан пересмотреть scope или способ исполнения; очередное сообщение «проверка продолжается» не является прогрессом.

На одну неизвестную проблему инструмента/окружения: до 2 целевых попыток или 10 минут активной диагностики, что наступит раньше. Затем отдельный infrastructure blocker с доказательствами и независимая задача. Для app/test FAIL — локализовать причину, исправить по плану; после 3 безрезультатных циклов вернуть product для перепланирования. Новый профиль, SHA или карточка не сбрасывают счётчик одной сигнатуры ошибки.

Здоровая длительная сборка с новым выводом не прерывается автоматически по этим числам. Продление диагностического окна product записывает ДО истечения: новая проверяемая гипотеза, ожидаемое доказательство и конечный срок. Нельзя бесконечно продлевать ту же попытку без новой информации. Таймаут не означает PASS и не отменяет обязательный критерий.

Не опрашивай неизменившийся лог/реестр/внешний blocker каждые несколько секунд. Используй события и ограниченные ожидания команд/CI; при внешней блокировке сохраняй checkpoint и продолжай доступную работу. Пользовательские обновления описывают новые результаты/блокировки; не считать частоту сообщений производительностью.

## Git и публикация

Для feature/fix — отдельная ветка от main либо явно проверенной зависимой базы. Сохраняй чужие изменения. Импортированный parent-коммит, в том числе падающий тест, не amend-ить. Собственный неопубликованный fix можно amend; опубликованный — только новый коммит. При общей истории используй fast-forward/cherry-pick --ff, если применимо, вместо пересоздания того же исправления с новым SHA и полного повторного smoke.

`Locally Ready` — все критерии карточки и её scope проверок выполнены, есть APPROVE прохода review с указанным review_mode и PASS/PASS_WITH_WARNINGS security gate для того же кандидата. `Ready to Publish` — финальная цепочка/этап прошла milestone-проверки, нет её блокирующих дефектов. Не выдавай локальную готовность за полную приёмку или отправку.

После gates `/product` выполняет обычный push проверенной task-ветки, проверяет remote ref, создаёт/обновляет PR при поддержке хостингом, ожидает обязательного CI и сливает по политике. При неизвестном исходе сначала читать remote, не плодить ветки/PR. Связанный bug публикуется в проверенной родительской цепочке, самостоятельный bug — fix-веткой. Не делать force-push/обход защиты; обязательный человеческий review остаётся внешней зависимостью.

Done требует подтверждённой интеграции на remote main и проверки результата. При отсутствии remote/ключа/merge-права сохранить blocker доставки; продолжать доступную локальную очередь. После фикса снять зависимость родителя по проверенной интеграции, не ждать закрытия bug в Done, если это создаёт взаимное ожидание. APK/AAB, ключи и local.properties не коммитить; Google Play release — отдельная задача.

## Состояние и локальный учёт задач

Источник истины — локальные файлы в workflow/. Trello не используется: не требуй подключения, не вызывай его инструменты и не создавай pending-операции синхронизации. «Доска» и «карточка» означают локальный реестр и запись задачи; profiles/*.md используют тот же контракт.

Реестр — `workflow/backlog.json`: `schema_version`, `tasks` со стабильными `id`, `kind` (epic/feature/bug/infrastructure), `title`, `parent_id`, `depends_on`, раздельными `development_status`/`delivery_status` и `task_path`. Подробный контракт, критерии и доказательства храни в `workflow/tasks/<id>/plan.md` и `state.json`; runtime-состояние цикла — в `workflow/loop-state.json`. Создавай файлы по необходимости, существующие ID и результаты сохраняй. Дедупликацию выполняй по реестру и состояниям задач; для багов сохраняй `dedup_key` из parent/scenario/signature. Записи обновляй атомарно; при нескольких процессах используй общий lease. В режиме одного агента отдельный сервис трекера не нужен.

При resume сначала читай локальный реестр, checkpoint и реальные изменения Git. Исторические внешние ID/URL сохраняй как необязательные ссылки; не выполняй их синхронизацию. Старые pending-операции Trello помечай отменёнными с причиной перехода на локальный учёт, сохраняя историю и содержимое задач. Отсутствующие локально данные не выдумывай. Поскольку runtime-файлы игнорируются Git, для переноса между машинами/харнессами передавай их отдельным checkpoint-архивом без секретов вместе с repo/branch/SHA и путями evidence; один clone не восстанавливает очередь.

Контракт: локальные task/parent ID и пути записей (внешний URL необязателен), цель/критерии/non-goals, план/версия, ветка/worktree либо выделенный checkout, depends_on, owned_paths, shared_contracts, integration_target, base/candidate SHA, validation_scope, сценарии/матрица, policy revision, report paths, pending patches и вопросы. Результат PASS/FAIL/BLOCKED с фактическими командами/exit и следующим шагом; исключение — ответ этапа review APPROVE; режим проверки сохраняется в отчёте.

Планы: `workflow/tasks/<id>/plan.md`; checkpoint задачи: `state.json` там же; цикл: `workflow/loop-state.json`; отчёты: `reports/<id>/<run>/`; сценарии Android: `tests/smoke/android/` либо явно зарегистрированный реестр проекта. Runtime workflow/reports игнорируются Git; исходники/тесты/сценарии входят в кандидат. Не создавать новый SHA из-за записи отчёта.

Перед созданием bug ищи дубликат по задаче/сценарию/сигнатуре. Expected/actual, SHA/APK для Android, шаги, приоритет и evidence обязательны. Повтор обновляет локальную запись. App bug, ошибка теста и infrastructure blocker различаются; не заводи новый app bug на каждую неудачную команду инструмента. Сводку и ссылки на evidence сохраняй в записи задачи, файлы — в локальном отчёте; не заявляй внешнюю загрузку.

Один текущий агент выполняет координацию и профили, WIP=1. При наличии стороннего процесса проверяй его lease/фактическую активность; истёкший lease не разрешает вмешиваться в живую работу. Перед FAIL сохрани все результаты и pending_integration. Resume начинается с сохранённых патчей либо нужной проверки, не с переписывания задачи.

Single_task сохраняет mode=single_task, task_limit=1, discovery_enabled=false; связанные исправления допустимы. Continuous продолжает независимые задачи до исчерпания доступной очереди/цели или лимитов. Внешние blockers остаются видимыми, их не опрашивают бесконечно. При выходе сохранить IDLE/BLOCKED/CHECKPOINTED/COMPLETED по фактам; файлы инструкций сами не обеспечивают фоновое пробуждение.
