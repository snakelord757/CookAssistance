# Правила работы CookAssistance

Прежде чем приступить к любой задаче, проанализируй условия и составь ёмкий план. Выполняй решение строго по плану. Если новые факты требуют изменения плана, сначала зафиксируй новую версию и причину, затем продолжай. Для разработки подробный план готовит `/planer`.

## Выбор профиля

Если сообщение начинается с `/имя_профиля`, прочитай соответствующий файл ниже и выполняй его инструкции вместе с этим файлом. Остаток сообщения — входные данные задачи. `/planner` — совместимый псевдоним `/planer`. Каноническое имя — `planer`.

| Команда | Файл | Назначение |
| --- | --- | --- |
| `/product` | [profiles/product.md](profiles/product.md) | Развитие продукта, backlog, координация |
| `/planer` | [profiles/planer.md](profiles/planer.md) | Исследование и план |
| `/tech` | [profiles/tech.md](profiles/tech.md) | Технические решения и зависимости |
| `/dev` | [profiles/dev.md](profiles/dev.md) | Реализация функции |
| `/bugfix` | [profiles/bugfix.md](profiles/bugfix.md) | Диагностика и исправление регрессии |
| `/review` | [profiles/review.md](profiles/review.md) | Независимое ревью коммита |
| `/unit-test` | [profiles/unit-test.md](profiles/unit-test.md) | Покрытие и прогон unit-тестов |
| `/smoke_scenario` | [profiles/smoke_scenario.md](profiles/smoke_scenario.md) | Smoke-сценарии |
| `/smoke` | [profiles/smoke.md](profiles/smoke.md) | Выполнение smoke через MCP |

Это соглашение маршрутизации текстовых запросов, а не регистрация команд в интерфейсе. Если клиент перехватывает команду (например, встроенную `/review`), используй `Профиль: review. Задача: ...`. Обрабатывай такую запись идентично `/review`. В вызове дочернего агента явно передавай путь к профилю и требование прочитать его: файлы `profiles` не загружаются автоматически.

## Контекст execution loop

Git и Trello уже настроены. Используй существующий репозиторий и подключённую доску; не запускай их повторную настройку. `/product` получает рабочий контекст из проекта, подключённых инструментов и сохранённого состояния. При необходимости сохраняет найденные значения в `workflow/project.md`:

- Цель продукта, аудитория, границы MVP, направления смежного развития, исключения и критерии завершения текущего этапа.
- Репозиторий, основная ветка, политика PR/слияния, разрешение публикации изменений.
- Стек и версии из исходников/манифестов; команды установки, сборки, unit-тестов, покрытия, запуска и остановки приложения.
- Trello board ID, ID списков и меток, MCP-инструменты; адрес тестовой среды, способ авторизации, тестовые данные и очистка.
- Заданные пользователем лимиты запуска, ограничения параллелизма и разрешённые классы библиотек и продуктовых изменений.

Перед запуском подтверди факты: `repo_root` через `git rev-parse --show-toplevel`, HEAD, основную ветку, состояние исходников, команды тестов и доступный MCP-инструмент smoke. Подключение Git не гарантирует наличия checkout в текущем каталоге. Если checkout отсутствует, найди указанный проект или запроси путь; `git init` выполняй только по явному поручению пользователя. Не выдавай неподтверждённый preflight за успешный.

Отсутствие `workflow/project.md` не блокирует запуск: это кэш контекста, а не обязательный этап настройки. Не выдавай предположения за настройки. Недостающие сведения сначала ищи в проекте и подключённых источниках. Обратимые технические решения принимай самостоятельно в рамках ТЗ; неизвестные цели продукта, доступы и разрешения не придумывай. Блокируй только зависимую работу.

Команда `/product` запускает execution loop, описанный в `profiles/product.md`; ТЗ в сообщении уточняет его цель, а без ТЗ источником работы служит текущая доска. Команда `/product resume` продолжает сохранённый цикл. Режим `consultation` не запускает цикл.

По умолчанию `/product` не только выполняет исходное ТЗ, но и самостоятельно формирует и реализует смежные функции по правилам `profiles/product.md`. Исходный список функций задаёт отправную точку, а не закрытый backlog. Развитие должно сохранять цель, аудиторию и связность пользовательских сценариев; новые направления продукта не вводятся молча. Если пользователь явно ограничил работу исходным ТЗ, смежное развитие отключается.

Поручение профилю означает реальный вызов отдельного дочернего агента доступным инструментом делегирования, ожидание результата и его обработку. Не ограничивайся рекомендацией пользователю вызвать следующий профиль. Передавай агенту корневые инструкции, файл профиля и контракт задачи. Используй дочерних агентов текущей задачи, а не создавай новые пользовательские чаты. При отсутствии свободного слота дождись завершения текущего агента; при отсутствии инструмента делегирования сохрани блокировку, не имитируй независимое ревью.

При четырёх слотах корневой агент сам исполняет `/product`: root + один `/dev` или `/bugfix` + два проверяющих. Не добавляй отдельного координатора поверх этой цепочки. Если все слоты заняты ожидающими родителями, агент, которому нужна консультация, возвращает родителю `BLOCKED` с `reason=CONSULTATION_REQUIRED`, вопросом, нужным профилем и `resume_phase`, затем завершает этап. Родитель после освобождения слота получает консультацию и возобновляет этап; это запрос координации, а не внешняя блокировка. Ожидание слота допустимо только если есть независимо работающий агент, который может его освободить.

## Общий контракт передачи задачи

Передавай: task ID/Trello URL, тип задачи, цель, критерии приёмки, границы изменений, зависимости, план и его версию, ветку/worktree, базовый и текущий commit SHA, пути к отчётам, нерешённые вопросы. Передавай также `run_id` и `parent_task_id`, чтобы исключить повторный запуск.

Результат агента содержит статус `PASS`, `FAIL` или `BLOCKED`, факты, изменённые файлы, точный SHA, команды и коды завершения, отчёты и следующий шаг. Исключение — успешный `/review`: его ответ ровно `APPROVE`; вызывающий агент сохраняет связь ответа с проверенным SHA. `APPROVED` не используется.

Сохраняй планы в `workflow/tasks/<task-id>/plan.md`, состояние задачи в `workflow/tasks/<task-id>/state.json`, состояние цикла в `workflow/loop-state.json`, отчёты в `reports/<task-id>/<run-id>/`, smoke-сценарии в `tests/smoke/`. Эти каталоги создаются по мере работы. Не записывай секреты, токены и персональные данные в отчёты.

Исходники, unit-тесты и smoke-сценарии входят в проверяемый Git-кандидат. Версионируй план явно внутри файла; планы, checkpoint и отчёты храни вне кандидатного дерева либо в явно исключённых runtime-каталогах (`workflow/`, `reports/` для этого проекта). Не исключай исходники или тесты ради чистого статуса. Запись runtime-отчёта не меняет candidate SHA. Перед проверкой убедись, что отслеживаемые кандидатные файлы неизменны и нет незакоммиченных новых исходников/тестов/сценариев; игнорируемые runtime-артефакты допустимы.

## Координация и восстановление

- `/product` — единственный координатор очереди и переходов карточек. Агенты тестирования могут создавать/обновлять дефекты по правилам ниже. Консультация `/product` из `/planer` возвращает ответ, а не запускает новый пайплайн.
- Состояния: `Inbox → Planning → Ready → In Progress → Review → Validation → Ready to Merge → Done`. `Blocked` доступен на любом шаге; после устранения причины возобновляй сохранённый этап. Названия связываются с реальными ID списков Trello в настройках.
- По умолчанию одна задача разработки одновременно. `/unit-test` и `/smoke_scenario` работают параллельно в отдельных worktree либо с непересекающимися файлами; назначенный `/dev` или `/bugfix` единолично интегрирует их результаты в ветку задачи. `/product` отвечает за интеграцию в основную ветку.
- В состоянии храни этап, владельца, heartbeat, срок lease, SHA, номера попыток, ID дочерних агентов, ссылки на отчёты и время следующей попытки. Захватывай задачу атомарно через доступное хранилище блокировок. Trello-карточка сама по себе не является надёжной блокировкой. Без такого хранилища допускается только один экземпляр координатора.
- Перед повтором сначала проверь живого исполнителя, состояние Git, карточку и сохранённый результат. Истёкший lease не разрешает запуск дубликата, пока прежний исполнитель не остановлен или не подтверждена его недоступность.
- После каждого этапа сохраняй checkpoint. После перезапуска продолжай с него, проверив актуальность SHA и результатов.
- Один цикл: до 3 итераций исправление–ревью и до 2 повторов временной ошибки инструмента. При исчерпании запиши `BLOCKED`, причину, уже выполненные попытки и условие возобновления; переходи к независимой задаче. Не объявляй успех ради завершения цикла. `/product` не сбрасывает счётчики без новых данных или изменения причины сбоя.
- Соблюдай заданные пользователем и средой лимиты. Отсутствие отдельного бюджета в файле настроек не ограничивает цикл одной задачей: продолжай брать готовые задачи до условий выхода из `profiles/product.md`. При достижении лимита сохрани checkpoint и заверши запуск. Не обходи ограничения среды.

## Git и критерии завершения

Каждая функция и каждый фикс выполняются в отдельной ветке от подтверждённой основной ветки: `feat/<task-id>-<slug>` или `fix/<task-id>-<slug>`. Не переключай общий checkout под другим агентом, не трогай чужие изменения. Зависимые изменения сначала интегрируются либо явно учитываются в плане.

Для `/dev` и `/bugfix` обязателен цикл независимого ревью. Ревьюер читает весь diff задачи относительно базы, даже если ему передан последний коммит. Исправления добавляй через amend только в собственный неопубликованный коммит задачи. Для опубликованных/общих коммитов используй новый коммит, не переписывай чужую историю. После любого изменения передавай ревьюеру новый SHA.

После первичного `APPROVE` параллельно запускай `/unit-test` и `/smoke_scenario`. Дождись обоих, интегрируй результаты. Изменения тестов/сценариев тоже требуют ревью итогового SHA. Затем на неизменяемом итоговом SHA выполни unit-прогон и новым агентом `/smoke` все smoke-сценарии. Не запускай smoke против старой сборки. Любая последующая правка аннулирует одобрение и проверки для прежнего SHA.

`Ready to Merge` требует: выполнен план и критерии приёмки, независимый `APPROVE`, успешны unit-тесты и все smoke, нет открытых блокирующих дефектов; все доказательства относятся к одному итоговому SHA. Пропуск, недоступность MCP и отсутствие тестов не считаются успешной проверкой.

`Done` требует интеграции в основную ветку и проверки результата интеграции. Автослияние допустимо только при заранее заданной политике, разрешении и прохождении проверок защищённой ветки. Без такой политики оставляй `Ready to Merge`, продолжай другие задачи. При изменении базы/конфликте повтори необходимые проверки интеграционного результата; не переноси старый успех автоматически.

## Дефекты и Trello

Перед созданием карточки ищи дубликат по task ID, сценарию/тесту и сигнатуре ошибки. Повторное падение дополняет существующую карточку. Укажи ожидаемое/фактическое поведение, шаги воспроизведения, приоритет, окружение, SHA, команду, лог и ссылку на исходную задачу. Приложи отчёт доступным способом; локальный путь не заменяет доступное вложение. Если загрузка недоступна, сохрани отчёт и pending-операцию, не заявляй, что отчёт прикреплён.

Ошибка приложения создаёт bug; ошибка доступа/инфраструктуры создаёт infrastructure blocker. При недоступности Trello сохраняй pending-операции с ключами дедупликации в состоянии и синхронизируй при восстановлении. Карточка от тестов не запускает вложенный бесконечный пайплайн: `/product` связывает её с текущей задачей, выбирает одного исполнителя и приостанавливает зависимую задачу. Новый фикс — отдельная ветка; интеграция его результата требует повторной проверки родительской задачи.

## Передача управления

`/product → /planer → /dev или /bugfix → /review ↔ исправления → (/unit-test || /smoke_scenario) → ревью изменившегося SHA → итоговый unit-прогон → /smoke → /product → следующая задача`.

Каждый исполнитель возвращает результат вызывающему агенту. Только `/product` выбирает следующую карточку. Завершение одной карточки не завершает execution loop, если есть другая доступная работа.
