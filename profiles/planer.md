# Профиль /planer

Прочитай корневой `AGENTS.md`. `/planner` — псевдоним этого профиля. Вход: ТЗ/локальная карточка, тип feature/bug, критерии и контекст проекта. Все этапы выполняет текущий агент; консультация означает чтение соответствующего профиля и выполнение его инструкций с последующим возвратом к плану.

Android-план опирается на [ANDROID.md](../ANDROID.md): Compose, UiState/события, Navigation, данные по необходимости, adaptive windows, lifecycle/ошибки. Укажи module/variant, API/permissions, Gradle tasks, instrumentation и AVD-матрицу UI smoke доступным драйвером. Если приложения нет — bootstrap отдельной задачей. Для документации применяй ограниченный scope из AGENTS.md. Публикация следует политике remote и не подменяет локальную готовность.

1. Проверь размер задачи: один самостоятельный результат, фича или воспроизводимый баг. Если результатов несколько, по `profiles/product.md` выполни декомпозицию и обнови локальный реестр до разработки. Укажи owned_paths, shared_contracts и depends_on. Изучи исходники, манифесты, архитектуру, тесты, историю и зависимости; опирайся на фактический стек.
2. Для продуктового решения прочитай `profiles/product.md` и выполни режим consultation; для технического — `profiles/tech.md`. Сохрани факты, допущения и решения, затем продолжи планирование. Не запускай отдельные агенты и второй execution loop.
3. Проверь противоречия ТЗ, совместимость, миграции, ограничения, риски и границы. Изменение цели оцени на этапе product до реализации.
4. Запиши в `workflow/tasks/<id>/plan.md` версию плана: цель/non-goals, исследованные файлы/стек, 2–5 критериев, шаги/файлы/модули, решения, тесты, smoke, откат, зависимости, риски. Зафиксируй validation_scope=task/fix/milestone, конечный набор сценариев/конфигураций и причину выбора. Каждому критерию назначь проверку. Для бага добавь воспроизведение, good/bad SHA и план диагностики.
5. При отсутствии блокирующих вопросов сохрани PASS; внутри product-loop продолжи по profiles/dev.md либо profiles/bugfix.md, при прямом запросе планирования верни план без реализации. Иначе сохрани BLOCKED с причиной и на этапе product выбери доступную работу.

Для смежной функции изучи гипотезу, решение отбора и `workflow/product.md`. Проверь точку входа, общие данные и сквозной путь; при чрезмерном scope выбери меньшую версию на этапе product до dev. Во время планирования функциональность не реализуй. Изменённый план версионируй и свяжи с checkpoint этапа реализации.
