# Профиль /dev

Прочитай корневой `AGENTS.md`. Вход: готовый план `/planer` и полный контракт задачи. Профиль выполняет текущий агент; переход к другому профилю означает чтение его файла и последовательное выполнение инструкций без создания субагентов.

Для Android соблюдай [ANDROID.md](../ANDROID.md): Compose-only UI, адаптивность, Kotlin-first API и наблюдаемые semantics для UI-автоматизации. Проверки выбирай по validation_scope, а инструменты — по фактическим возможностям среды. Unit/Compose tests не заменяют smoke на запущенном эмуляторе.

1. Подтверди применимость плана, критерии и зависимости. Используй отдельную task-ветку от проверенного base SHA; worktree необязателен, достаточно выделенного checkout. Сохраняй чужие изменения. Соблюдай owned_paths; изменение общего контракта сначала оцени по `profiles/product.md` в режиме consultation и обнови решение, затем вернись к dev.
2. Выполни план поэтапно, сохраняя совместимость за пределами задачи. При противоречии прочитай `profiles/planer.md`, обнови версию плана и вернись к сохранённому этапу dev.
3. Добавляй unit-тесты вместе с кодом. До финального review прочитай и выполни `profiles/unit-test.md` и `profiles/smoke_scenario.md` в назначенных границах. Сохрани результаты в состоянии задачи.
4. Выполни предусмотренные scope проверки; для Android это назначенные build/lint/unit/instrumentation. Подготовь полный незакоммиченный снимок кандидата по AGENTS.md; commit до security gate запрещён. Прочитай `profiles/review.md` и выполни отдельный проход review всего diff с зафиксированными base SHA и снимком кандидата. Это самопроверка тем же агентом, что явно отражается в отчёте.
5. При замечаниях вернись к dev, исправь причину и повтори затронутые проверки и review нового снимка в пределах лимитов. Собственный неопубликованный коммит можно amend; опубликованный изменяй новым коммитом.
6. Для Android собери APK, сохрани SHA-256/build provenance, variant/applicationId и матрицу. Прочитай `profiles/smoke.md` и выполни согласованный scope. После изменения кандидата повтори затронутые проверки; завершённые результаты переноси только по правилам AGENTS.md.
7. При выполнении внутри product-loop вернись к его этапу SECURITY после PASS проверок по profiles/product.md; при прямом запросе dev заверши отчёт в пределах запроса. Результат: итоговый SHA, review/unit/smoke, отчёты, `Locally Ready` (task), `Ready to Publish` (milestone) либо блокировка. `Done` требует подтверждённой интеграции на remote.

На переходах сохраняй checkpoint и resume_phase. При resume используй существующую ветку и результаты; не создавай повторную реализацию. Побочные фичи и независимые баги заноси в локальный реестр, не расширяя scope.

`PASS` допустим с доказательствами всех обязательных проверок. При app/test FAIL создай/обнови локальный дефект, сохрани отчёт и перейди через product/planer в bugfix. При недоступном инструменте — `BLOCKED`. Сохраняй pending_integration для ещё не применённых патчей; сначала интегрируй их, затем продолжай review.

При прямом запросе профиля security gate также обязателен до commit. Генерация и исправления проходят только через [Gateway](../docs/llm-gateway.md).
