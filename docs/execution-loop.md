# Исполняемый security execution loop

Рабочий запуск допускается только из [защищённой установки runtime](runtime-integrity.md).
Редактируемая source-копия не является доверенной; прямой CLI-запуск блокируется.


Выбранная конфигурация: [локальная защита + review той же моделью](model-security-review.md).
Один `--adapter-config` используется для генерации и отдельного security-запроса.

Python 3.11+ и Git, без дополнительных Python-пакетов. Исходники:
[координатор](../scripts/execution_loop.py), [обязательный flow](../scripts/execution_flow.py), [встроенный гейт](../scripts/context_gate.py),
[DLP/локальный клиент/аудит](../scripts/loop_security.py), [адаптеры моделей](../scripts/model_adapters.py), [допуск контекста](../scripts/context_release.py), [тесты](../tests/test_execution_loop.py).

Это отдельный CLI. Он не перенаправляет внутренние запросы Codex/IDE и не является Android backend. Перед всеми LLM-вызовами **этого CLI**, включая исправления, данные проходят встроенный локальный гейт. `run()` сам создаёт `ContextGate` и `GuardedFlow`; выключателя/режима обхода нет. Пользователю не нужно запускать отдельный сервис, указывать адрес гейта, получать его токен или привязывать его к модели. Сам Gateway не вызывает модель, не содержит model/endpoint/API-ключа провайдера и не разбирает её ответы. Модель подключается отдельным адаптером execution loop; ограничения данных остаются одинаковыми для любого адаптера.

## Запуск

Перед запуском выполните [контракт подключения](harness-contract.md) и установите
штатный commit hook через `install-hook` в standalone clone. CLI проверяет его
наличие и запускает поведенческий preflight; без них выполнение блокируется.

Работайте в отдельном чистом checkout с настроенными Git author/name. Контроллер запускайте из доверенной копии инструментов, вне изменяемого проекта. В checkout не должно быть чужих staged/unstaged/untracked файлов. Настройка и audit-файлы должны находиться снаружи checkout либо в игнорируемом runtime-каталоге.

Для обычного execution loop `LOOP_GATEWAY_TOKEN` и отдельный процесс Gateway не нужны. Если выбран сетевой адаптер модели, его credential задаётся через `LLM_UPSTREAM_TOKEN` штатным secret manager; не помещайте ключ в argv или JSON. Это credential модели, не настройка гейта. Конфиг, например `D:/runtime/task.json`:

```json
{
  "task": "Implement input validation in the allowlisted module",
  "files": ["src/validation.py"],
  "tests": [["python", "-m", "unittest", "discover", "-s", "tests"]],
  "max_attempts": 3,
  "test_timeout": 300
}
```

`files` — точный allowlist исходников и необходимого контекста; отсутствующий файл можно создать. Модель возвращает полные замены файлов, а не shell-команды. Удаления, произвольные пути, symlinks/junctions, `.git`, секретные файлы и изменение самого контроллера запрещены. Большой контекст блокируется, не обрезается молча. Файлы с обезличенным содержимым доступны только для чтения: попытка перезаписать их блокируется, секреты в сгенерированный код автоматически не восстанавливаются. Имена файлов можно заменять нейтральными alias; обратное отображение выполняется только локально. Файлы с необходимыми зависимостями включайте явно; недостаточный контекст должен давать BLOCKED в review.

`tests` — доверенные argv-массивы, не строки shell. Для Android задайте предусмотренные планом Gradle-команды и UI-проверки, используя исполняемый wrapper/launcher своей ОС. CLI не выводит результаты тестов в LLM: при FAIL отправляется только фиксированное сообщение. В stdout/stderr дочерних тестов могут быть секреты, поэтому они не сохраняются в audit. Подробную диагностику выполняйте отдельно с локальной очисткой логов.

```powershell
python -I -S -B 'C:/Program Files/CookSecurity/runtime-v1/scripts/trusted_runtime.py' run --repo D:/isolated/task --config D:/runtime/task.json --audit D:/runtime/loop.jsonl --release-policy D:/private/releases.json --adapter-config D:/runtime/adapter.json
```

Без `--commit` цикл оставляет проверенный staged-кандидат и подписанное разрешение в Git metadata. Чтобы цикл сам создал коммит, используйте `--commit` при запуске. Exit 0 означает PASS/PASS_WITH_WARNINGS; exit 2 — BLOCKED. Исправления при High/Critical и тестовом FAIL ограничены тремя попытками. После BLOCKED файлы остаются для диагностики; обычный повтор из грязного checkout запрещён. После локального допуска security-запроса используйте `--resume-stage security` (тесты повторяются); для генерации исправления — `--resume-stage generation` (сохраняется feedback, привязанный к HEAD/исходникам). Возобновление допускает только изменения файлов из allowlist. Не делайте reset поверх своей работы: сначала сохраните diff и создайте чистый отдельный checkout.

## Подключение моделей — вне Gateway

Интерфейс адаптера: `complete(public_payload, audit, request_id) -> JSON result`. Он получает только одобренный публичный объект, без исходного контекста и таблицы приватных замен. Вызов адаптера расположен после успешной локальной проверки; при BLOCK он не вызывается. Качество ответа и схема генерации/security review проверяются координатором, а не определяют совместимость Gateway.

В поставке два примера сетевых адаптеров:

- `chat-completions`: преобразует разрешённый контекст в messages и разбирает choices/JSON mode.
- `json-http`: отправляет разрешённый JSON как есть и получает JSON-результат; не требует model, messages, choices или finish_reason.

Пример `adapter.json` для второго варианта:

```json
{"type": "json-http", "endpoint": "https://service.example.invalid/infer"}
```

Для Chat Completions используйте `type: "chat-completions"` и добавьте `model`. Это настройка конкретного адаптера, **не Gateway**. Оба примера используют Bearer credential из окружения координатора. По умолчанию требуется HTTPS; для локального сервиса можно явно указать `local: true` — тогда разрешён только `http://127.0.0.1`. Redirect/fallback запрещены этими HTTP-адаптерами. Локальная модель без HTTP или другой API реализуют тот же Python-интерфейс; передайте объект backend в `execution_loop.run(..., backend, audit, releases=policy)`. Встроенный гейт применяется автоматически; менять его или policy при смене модели не требуется. Policy меняется только при изменении самих раскрываемых данных, независимо от выбора модели.

Адаптер — доверенный код интеграции. Для произвольного API готовый адаптер не обещается; независимость локальных ограничений от модели не означает универсальную совместимость HTTP-протоколов.

## Место гейта во flow

`контекст → встроенный допуск/обезличивание → генерация → тесты → встроенный допуск review-контекста → отдельный security review → решение → коммит либо исправление через тот же гейт`

Оба вызова LLM, исправления по High/Critical и повторные попытки идут через единственный `GuardedFlow.call()`. `run()` принимает backend модели, а не произвольный клиент с методом `call()`: обязательный flow создаёт сам координатор. Backend получает только результат допуска. Если policy отсутствует, audit недоступен или контекст не согласован, backend не вызывается, commit не разрешается. Изменение модели не изменяет эту последовательность.

Для других приложений сохранён необязательный HTTP-интерфейс [llm_gateway.py](../scripts/llm_gateway.py): локальный `POST /v1/authorize` и `context_gate.GatewayClient.authorize()`. Ему нужны собственные local token/адрес, но **execution loop от этого сервиса не зависит**. Отдельно использовать локальную проверку без HTTP можно через `ContextGate.authorize()`.

## Gate коммита

Security review — отдельный запрос с [Android-промптом](security-review-prompt.md), исходными и новыми версиями файлов, snapshot ID. Неполный coverage, неизвестная severity, невалидные JSON/строки/пути блокируют цикл. Critical/High возвращаются в генерацию с file/line/fix, затем повторяются тесты и review. Medium/Low создают `security_warning`; чистый ответ даёт PASS.

Разрешение связано с base HEAD, staged tree и snapshot и подписано локальным HMAC-ключом. После review проверяются HEAD, индекс, исходники и посторонние изменения. `--commit` создаёт объект ровно из одобренного tree и атомарно обновляет HEAD, только если base не изменился. Никакого `git add .`, force push или автоматической публикации нет.

Автокоммит использует Git plumbing и потому запрещён при чужих активных hooks/core.hooksPath: такой репозиторий требует отдельной проверенной интеграции. Текущий CLI блокируется и не заменяет чужие hooks. Если audit-диск отказал уже после атомарного обновления HEAD, CLI явно сообщает `committed_but_final_audit_failed_inspect_HEAD`; сначала проверьте HEAD, не повторяйте коммит вслепую.

Для CLI `run`/`review` обязателен pre-commit hook; установите его **в отдельном standalone clone**:

```powershell
python -I -S -B 'C:/Program Files/CookSecurity/runtime-v1/scripts/trusted_runtime.py' install-hook --repo D:/isolated/task
```

Hook вызывает `verify`: без валидного разрешения на текущие HEAD/tree коммит отклоняется. После успешного коммита разрешение устаревает. Существующие hooks/core.hooksPath не перезаписываются; для linked worktree установка запрещена, поскольку hooks общие. Не удаляйте доверенную копию контроллера, пока hook используется.

## Защита данных и границы

Перед отправкой требуется явный допуск точного обезличенного запроса по [процедуре disclosure](context-release.md). Проверяются task, весь выбранный контекст, system/user messages и feedback. Gateway независимо проверяет тот же допуск и строит upstream-запрос из разрешённого export; произвольные сообщения клиента не пересылаются. После этого дополнительно сканируются экспорт и ответ. JSON сначала декодируется: `\u0040` не обходит проверку email. При обнаружении блокируется весь запрос/ответ, без частичной отправки или автоматического удаления контекста. Секретные файлы не включаются по умолчанию; генерация с секретом не применяется к checkout.

Отсутствие срабатывания детектора НЕ разрешает отправку. Без exact release блокируются и неизвестные ФИО/адреса/нестандартные токены, и вообще любой новый контекст. Детекторы дополнительно покрывают известные форматы provider tokens, private keys, JWT/bearer, credential assignments/URLs, email, международные телефоны, SSN и высокоэнтропийные строковые литералы. Это консервативная эвристика: возможны ложные срабатывания; произвольные ФИО, адреса, нестандартные токены и намеренно закодированные значения универсально не распознаются. Оператор обязан локально просмотреть весь export, обезличить чувствительные значения, а сомнительное оставить без допуска. Автоматического одобрения или режима «только regex» нет. Качество ручной классификации остаётся доверенной границей; для большой базы подключите организационную DLP/локальную классификацию, не снимая exact-release gate. `ALLOW_CLEAN` означает отсутствие срабатываний этих детекторов, не абсолютную гарантию.

Audit JSONL содержит только время, policy, этап, request ID, release ID, направление, verdict, rule/count, факт попытки upstream и snapshot. Payload/токены/PII/произвольные исключения не логируются. Gateway пишет BLOCK/RELEASED локально; событие SEND пишет отдельно сетевой адаптер после допуска; audit failure останавливает отправку. SEND означает начало попытки, а не доказанную доставку. Request IDs связывают проверки и отдельные LLM-вызовы. Логи держите вне репозитория с доступом только оператора и нужным сроком хранения.

Локальный hook/HMAC защищает от случайного обхода и подмены результата моделью через файловый протокол, но не от владельца машины с правом менять `.git`, использовать `--no-verify` или Git plumbing. Для обязательного командного enforcement нужны CI/server-side gates и branch protection. Сам CLI не устанавливает firewall и не перенаправляет чужие LLM-клиенты.

**Исполнение тестов — граница доверия:** сгенерированный код может выполняться тестами. Запускайте checkout в изолированной VM/container без личных файлов, секретов и внешнего egress; Модельные credentials держите только в доверенном процессе координатора/адаптера, не в тестовом sandbox. Локальному Gateway они не нужны. CLI не является OS sandbox. Два известных токена исключаются из окружения тестов, но это не изолирует остальные файлы/переменные. Доверенные acceptance tests держите вне разрешённых модели файлов.

## Проверка

```powershell
python -m unittest discover -s tests -p test_execution_loop.py -v
```

Suite использует реальный HTTP Gateway и временные Git-репозитории; только upstream заменён детерминированным синтетическим провайдером. Проверяются clean commit, High → fix → повторный review, Critical без коммита, Medium/Low warning, DLP до отправки/применения, отказ аудита, неполный ответ, stale snapshot и pre-commit hook. Это подтверждает механику цикла, но не качество реальной модели и не live-подключение к вашему upstream.
