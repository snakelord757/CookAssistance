# Защита gateway от изменения агентом

Начальный шаг запуска — [bootstrap gateway](gateway-bootstrap.md): первая установка,
затем проверка готовности при каждом запуске.


Изменяемая копия исходников не является рабочей установкой gateway. Проверка
хеша внутри файла, который агент может переписать вместе с хешем, защиты не даёт.
Поэтому production entry point теперь — `trusted_runtime.py` в отдельной
установке с владельцем, отличным от ограниченной учётной записи агента.

## Что проверяет код

- До импорта gateway/контроллера launcher проверяет точный состав установки,
  SHA-256 всех исполняемых модулей и security-промпта по `runtime-seal.json`.
- Проверяет права ОС: запись, удаление/подмена, изменение ACL/владельца,
  возможность замены через родительские каталоги. Файлы, принадлежащие агенту,
  нельзя объявить защищёнными простым readonly-флагом. Symlink/junction/hardlink,
  лишние модули, bytecode и пакеты в runtime блокируются.
- На Windows проверяются реальные права через CreateFile и привилегии токена,
  включая отключённые, которые процесс может включить. Привилегированный
  процесс с возможностью вернуть себе запись не принимается. На Unix root,
  собственник и процесс с Linux capabilities также не принимаются.
- Python запускается с `-I -S -B`: без PYTHONPATH, cwd, пользовательского site и
  записи bytecode. Сам Python/stdlib и ОС остаются доверенной базой и должны
  быть установлены оператором вне прав записи агента.
- CLI также требует защищённых task/model/harness-config и release policy.
  Нельзя ослабить правила, поменяв настройки вместо gateway.
- Контроллер проверяет закреплённое содержимое перед/после LLM-вызовов,
  до/после тестовых команд и перед разрешением коммита. При изменении — BLOCKED;
  неуспешный цикл удаляет approval. Approval связан и с версией runtime.
- Allowlist генератора не может включать активный security-промпт или модули
  защиты. Commit hook запускает тот же проверяющий launcher.

## Установка оператором

После проверки исходников подготовьте новую, ещё не существующую директорию:

```powershell
python scripts/package_runtime.py --destination 'C:/Program Files/CookSecurity/runtime-v1'
```

Упаковщик копирует только фиксированный набор модулей и security-промпт, создаёт
seal. Он **не объявляет установку доверенной**, не меняет пользователей/ACL и
не пересобирает seal при обычном запуске.

Владелец установки и конфигов — оператор/администратор, которому агент не имеет
доступа. Агенту нужны только чтение/выполнение, без записи, удаления, смены ACL
или владельца. Проверьте также права родительских каталогов. Запускайте агент
и loop под отдельной ограниченной учётной записью, без возможности повысить
привилегии или менять код процесса контроллера. Для Unix эквивалент — отдельная
root-owned установка в `/opt`, агент без root/sudo/capabilities.

Не используйте автоматический `takeown`, выдачу себе прав или обновление seal
для «починки» BLOCKED: это разрушает границу доверия. Обновление установки —
отдельное действие оператора после review. Старая approval после обновления
runtime недействительна.

Все команды loop теперь выполняются через установленный launcher:

```powershell
python -I -S -B 'C:/Program Files/CookSecurity/runtime-v1/scripts/trusted_runtime.py' install-hook --repo D:/isolated/task
python -I -S -B 'C:/Program Files/CookSecurity/runtime-v1/scripts/trusted_runtime.py' run --repo D:/isolated/task --config C:/ProgramData/CookSecurity/task.json --adapter-config C:/ProgramData/CookSecurity/model.json --release-policy C:/ProgramData/CookSecurity/releases.json --audit D:/runtime-audit/loop.jsonl
```

Расположение само по себе не даёт доверия: реальные права проверяет launcher.
Конфиги и policy должны принадлежать оператору. Audit разрешено писать процессу,
но для защиты от удаления журналов нужен отдельный внешний сборщик.
Для `review` добавьте проверенный `--harness-config`, остальные требования
[контракта харнесса](harness-contract.md) остаются обязательными.

## Границы

Текущая рабочая копия специально не признаётся защищённой: она доступна агенту
для редактирования. Отдельный владелец и ограниченная учётная запись в этой
сессии не создавались. Поэтому production-запуск здесь даёт BLOCKED.

Прямые Python API нужны для доверенной интеграции и unit-тестов. Их in-process
pin обнаруживает изменение во время работы, но не заменяет launcher/права ОС
и не защищает от вредоносного кода внутри того же процесса.

Защищённый gateway не является firewall. Произвольный агент с shell может
попробовать вызвать другой клиент или удалить hook в своём checkout; local Git
metadata и HMAC не являются внешней подписью. Против намеренного обхода всего
пайплайна нужны egress-изоляция, отдельная commit authority/CI и branch protection.
Эта доработка не утверждает, что они настроены. Тесты сгенерированного кода
должны выполняться в отдельном sandbox без credentials и доступа к процессу
контроллера; readonly runtime не защищает память процесса от другого процесса
с той же идентичностью.

## Проверки

`test_runtime_integrity.py` проверяет изменение gateway и промпта во временных
копиях, пересчёт поддельного seal, добавление модулей/bytecode, запрет импорта
изменённого gateway, изменение защиты тестовой командой и во время review.
Отказ для изменяемой установки проверяется с настоящими Windows правами.
Положительная проверка hashes использует явно замоканную границу прав; успешный
production-запуск под отдельной ограниченной учётной записью пока не проверен.

Основания Windows-проверок: [права файлов](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights),
[привилегии, обходящие файловые ACL](https://learn.microsoft.com/en-us/windows-hardware/drivers/ifs/privileges).
