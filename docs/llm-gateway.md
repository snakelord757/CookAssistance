# LLM Gateway: локальное ограничение данных

Рабочий запуск допускается только из [защищённой установки runtime](runtime-integrity.md).
Редактируемая source-копия не является доверенной; прямой CLI-запуск блокируется.


Обязательное подключение: [контракт харнесса и поведенческий preflight](harness-contract.md).
Для security review используется [та же модель отдельным запросом](model-security-review.md)
с новым контекстом и отдельным security-промптом. Gateway по-прежнему не вызывает LLM.

Gateway — локальный независимый от модели слой допуска данных. Он не знает model ID, provider endpoint, API-ключ модели, Chat Completions, JSON mode или формат ответа модели. Его можно использовать без какой-либо LLM. В execution loop он встроен как [ContextGate](../scripts/context_gate.py) и [GuardedFlow](../scripts/execution_flow.py); необязательный HTTP-интерфейс — [llm_gateway.py](../scripts/llm_gateway.py); запуск и интеграция — в [руководстве CLI](execution-loop.md).

## Поток данных

`приватный локальный контекст → локальное обезличивание и exact release → Gateway → разрешённый публичный контекст → адаптер модели → любая выбранная модель`

Обязателен [явный допуск](context-release.md) точного обезличенного объекта. Allowlist файлов и отсутствие regex-срабатываний не дают права отправлять данные. Клиент проверяет привязку исходного контекста к разрешённому export; Gateway независимо сверяет публичный объект с операторской политикой. Политика находится вне генерируемого checkout и недоступна генератору для записи средствами ОС.

Нет допуска, он отозван, запрос изменился или данные сомнительны — BLOCK. Gateway не вызывает модель и не имеет исходящих сетевых вызовов. Он возвращает только проверенный export. В execution loop вызов отдельного адаптера расположен после успешного gate; адаптер получает только этот публичный объект, не исходники до обезличивания и не таблицу приватных замен.

## Обязательный шаг execution loop

`run()` сам создаёт локальный gate и общий flow перед любым обращением к backend. Отдельный сервис, адрес и токен Gateway не требуются. Генерация, исправления и security review используют один путь; отсутствие policy не включает fallback. Гейт не подключается к каждой модели: модель выбирается в существующем backend execution loop, а проверка данных остаётся неизменным шагом координатора.

## Необязательный локальный HTTP API

`POST /v1/authorize` на `127.0.0.1` с локальным Bearer-токеном. JSON содержит `request_id`, `release_id`, `payload`; payload — `{stage, system, context}`. Это внутренний формат данных приложения, не протокол какого-либо LLM-провайдера. Ответ: request/release IDs, policy revision и разрешённый payload. Ошибка — локальный отказ без передачи модели. `GatewayClient.authorize(...)` работает отдельно от генерации и коммита.

## Адаптеры — отдельная ответственность

[model_adapters.py](../scripts/model_adapters.py) содержит примеры HTTP-интеграций для execution loop: Chat Completions и обычный JSON endpoint. Для SDK, другого HTTP API или локальной модели реализуется `complete(public_payload, audit, request_id)`. Менять Gateway или его правила не требуется. Выбор конкретного адаптера и credential производится в координаторе, не в сервисе Gateway.

Независимость от модели не означает, что один HTTP-клиент автоматически поддерживает все API. Адаптеры — доверенный код, их транспортные требования относятся к ним. Встроенные вызовы Codex/IDE сами собой не перенаправляются: утверждать их защиту можно только после фактической интеграции.

## Проверки и аудит

Дополнительно сканируются разрешённый export и результат модели. Известные secrets/PII, ошибки DLP/аудита, неоднозначность замен, подмена или неполное разрешение дают отказ. Файлы с обезличенным содержимым доступны генератору только для чтения; автоматического восстановления приватных значений в сгенерированном коде нет.

Audit содержит только время, этап, request/release ID, policy revision, verdict и rule/count. Gateway пишет BLOCK/RELEASED; сетевой адаптер отдельно пишет SEND и результат фильтрации ответа. Gateway никогда не помечает данные как отправленные внешней модели. Payload, исходные значения замен, headers и тексты произвольных исключений не логируются. ALLOW_CLEAN обозначает только отсутствие срабатываний дополнительных детекторов, а не разрешение передачи.

Проверки используют синтетические данные: Gateway работает без модели; один и тот же gate применяется к Chat Completions, JSON endpoint и локальному Python-адаптеру; при отказе адаптер вообще не вызывается. Также проверяются обезличивание, подмена/отзыв разрешений, отдельный допуск review, Critical/High без коммита, Medium/Low warning, snapshot/HEAD gate. Реальная внешняя модель без авторизованного адаптера и credentials не считается проверенной.

Политика обеспечивает соответствие точному разрешению оператора, а не универсальное семантическое распознавание PII. Оператор локально проверяет весь export; сомнительные данные не допускаются. Принудительная защита других процессов/произвольного сетевого кода требует OS sandbox/ACL/egress policy; сам локальный сервис не является firewall.
