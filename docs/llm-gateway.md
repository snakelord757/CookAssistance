# LLM Gateway: обязательный контракт execution loop

Это контракт подключения существующего прокси «Дня 3», а не реализованный прокси. В репозитории на момент изменения нет его исходников, endpoint, схемы API и подтверждённой конфигурации харнесса. Пока подключение не подтверждено, live routing, DLP и отдельный LLM security review имеют статус BLOCKED. Backend приложения и его локальная модель не являются автоматически Gateway разработки.

## Подключение и границы

До первого LLM-запроса настрой клиент/харнесс на авторизованный Gateway и проверь документированный API. Зафиксируй безопасный идентификатор маршрута, policy revision и correlation ID; credentials передавай штатным механизмом аутентификации вне prompt. Не печатай headers, environment и URL с credentials. Не угадывай endpoint, аккаунт или секрет. Для удалённого соединения требуется HTTPS с проверкой сертификата.

Все этапы, консультации, генерация, review, security review, retries, fallback и feedback используют один обязательный gateway adapter. Запрети прямой egress к провайдерам средствами клиента/сети; отсутствие настройки маршрута или недоступность прокси останавливают LLM-этап. Не считай инструкцию в Markdown доказательством сетевого ограничения. Встроенные LLM-вызовы харнесса, которые нельзя перенаправить, означают BLOCKED для требования «весь loop».

## Данные до отправки

1. Собирай контекст по allowlist необходимых файлов/диапазонов. По умолчанию не включай .env, local.properties, credentials, keystore, дампы, пользовательские БД, реальные обращения пользователей и сырые логи. .gitignore не является DLP-политикой. Новые файлы, system/user messages, tool outputs, attachments, feedback и история подлежат той же проверке.
2. До помещения в prompt локально проверь контекст на секреты, токены, private keys и PII. Удали/замени значения, сохрани пути и исходные номера строк; при сомнении блокируй материал. Regex/entropy сами по себе не гарантируют отсутствие PII: нужен минимальный набор данных, детекторы Gateway и ручная оценка сомнительных мест. Не загружай весь репозиторий «для анализа».
3. Gateway повторно проверяет весь сериализованный запрос до upstream. При обнаружении чувствительных данных отклоняет его целиком (BLOCK); не пересылает даже часть/stream. Исправленный очищенный запрос проходит новый scan. При ошибке/таймауте детектора, отсутствии audit sink или неизвестном verdict — fail closed. Редактирование с потерей необходимого контекста блокирует review, а не даёт clean.
4. Ответ LLM также проходит проверку до логирования, применения и дальнейшего feedback. Запрещено сохранять raw request/response в SDK debug logs, traces и exception messages; только разрешённые метаданные. Находки hardcoded secret передаются как категория/расположение с REDACTED, без значения.

## Audit

Gateway пишет JSONL-события для каждого запроса и ответа: UTC timestamp, run/task/request ID, stage, direction, policy revision, detector rule IDs и counts, verdict (BLOCK / ALLOW_CLEAN / ERROR), upstream_sent, безопасный reason code. Не записывать payload, matched value, headers, PII, свободный текст исключений или хэши отдельных секретов. Идентификаторы задаёт координатор, не текст исходного кода. Доступ/срок хранения логов ограничиваются конфигурацией владельца Gateway.

ALLOW_CLEAN означает «назначенные детекторы не нашли чувствительных данных», а не доказательство отсутствия любых секретов. Warning security review — отдельное событие security_warning с severity, finding ID и безопасным относительным путём/строкой; FAIL — security_rejected. Audit и security report связаны request ID и snapshot ID.

## Приёмка подключения

Проверки выполняются только на синтетических данных, без реальных ключей и PII. Сохранить реальные результаты отдельно от ожидаемых; mock не закрывает live-критерий.

| Проверка | Ожидаемое доказательство |
| --- | --- |
| Синтетические secret/token/PII в каждом канале, включая feedback/tool output | BLOCK и rule/count; upstream_sent=false, upstream не получил запрос; canary отсутствует в логах |
| Очищенный запрос генерации и отдельный security-запрос | Два различных request ID, ALLOW_CLEAN; подтверждённый маршрут через Gateway |
| Прямой provider URL/fallback | Соединение запрещено, нет обхода при отказе Gateway |
| Ошибка детектора/аудита, timeout, malformed/truncated review, unknown severity | BLOCKED; commit не выполняется |
| Ответ Critical/High | Возврат в генерацию с file/line/fix; повторные тесты и новый security request |
| Ответ только Medium/Low | PASS_WITH_WARNINGS, warning для каждой находки, commit разрешён при остальных gates |
| Полное покрытие и пустой findings | PASS, commit разрешён только для проверенного снимка |
| Изменение staged/untracked после approval | Approval инвалидирован, commit запрещён до нового gate |

Для проверки ветвления допустимы детерминированные ответы тестового upstream за Gateway; помечай их synthetic. Дополнительно требуется реальный security-запрос к LLM через прокси. Логи BLOCK/ALLOW_CLEAN не создавать вручную как свидетельство работы Gateway.
