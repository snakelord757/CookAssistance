# TASKS — декомпозиция CookAssistance

Документ разбивает исходное ТЗ из 15 пунктов на отдельные задачи. Для каждой задачи заданы: цель, объём, зависимости и проверяемые **критерии готовности**. Связи «без этой фичи я не смогу реализовать этот функционал» зафиксированы явно: в задаче-источнике перечислены **требования к нижестоящим задачам** (например, mock-сервер должен отдавать не только список рецептов, но и праздничные подборки, тип блюда и «блюдо дня»).

Стек — из [ANDROID.md](ANDROID.md): Kotlin, Gradle Kotlin DSL + version catalog, Jetpack Compose + Material 3, single Activity, Navigation 3, ViewModel + immutable UiState + StateFlow + UDF, Ktor Client + kotlinx.serialization, Room + KSP, DataStore, Coil, Coroutines. Речь — Android `SpeechRecognizer`, озвучка — Android `TextToSpeech`.

## Задача 1 — Mock-сервер (локальный, рецепты)

**Цель.** Локально запускаемый сервер, отдающий моковые рецепты. Источник данных для всего клиентского функционала каталога.

**Объём.**
- Сервер запускается одной командой на машине разработчика (без внешнего интернета и авторизации).
- 10–15 рецептов, покрывающих разные типы блюд и праздники.
- Данные в памяти или в JSON-файле; изменение данных не требует пересборки Android-приложения.
- Технологию выбирает `/tech`: рекомендуется Ktor (JVM, консистентно Kotlin-first стеку) или FastAPI/Python; главное — фиксированный HTTP JSON-контракт ниже.

**Контракт API (обязателен для нижестоящих задач).**

| Метод | Путь | Назначение | Потребитель |
|-------|------|------------|-------------|
| GET | `/recipes` | список рецептов (сводка) | 3, 13 |
| GET | `/recipes/{id}` | полный рецепт | 4 |
| GET | `/recipes?type={type}` | фильтр по типу блюда | 13 |
| GET | `/recipes/dish-of-the-day` | один рецепт дня | 14 |
| GET | `/collections` | список праздничных подборок | 15 |
| GET | `/collections/{id}/recipes` | рецепты подборки | 15 |
| POST | `/feedback` | (опционально) приём обратной связи | 10 |

**Модель рецепта (поля обязательны).**

```json
{
  "id": "string",
  "title": "string",
  "description": "string",
  "type": "soup | salad | main | side | dessert | drink | baking | breakfast",
  "ingredients": [{ "name": "string", "amount": "number", "unit": "string" }],
  "steps": ["string"],
  "cookingTimeMin": "number",
  "servings": "number",
  "imageUrl": "string",
  "collections": ["holiday-id"]
}
```

**Требования к нижестоящим задачам (закрывают пробелы исходного ТЗ).**
- `type` обязателен для **13** (сортировка по типу блюда).
- `/recipes/dish-of-the-day` обязателен для **14** (блюдо дня).
- `/collections` + `/collections/{id}/recipes` обязательны для **15** (праздничные подборки) — в исходной формулировке задачи 1 этого нет, но без серверной части подборки реализовать нельзя.
- Полная деталка (`ingredients`, `steps`, `cookingTimeMin`, `servings`) обязательна для **4**.
- `imageUrl` обязателен для **3/4** и кэширования в **11**.
- Если для **10** выбран серверный канал отправки — добавить `POST /feedback` (см. задачу 10).

**Критерии готовности.**
- [ ] Сервер запускается одной командой и отвечает на `localhost`.
- [ ] `GET /recipes` возвращает 10–15 рецептов валидным JSON по контракту.
- [ ] `GET /recipes/{id}` возвращает полный рецепт со всеми обязательными полями.
- [ ] Поле `type` заполнено у всех рецептов и покрывает хотя бы 4 разных типа.
- [ ] `GET /recipes/dish-of-the-day` возвращает ровно один рецепт.
- [ ] `GET /collections` и `GET /collections/{id}/recipes` работают; есть ≥2 праздничные подборки с ≥2 рецептами каждая.
- [ ] Автотесты сервера (контракт ответов, структура JSON) проходят.
- [ ] Документированы команда запуска и порт.

## Задача 2 — Основа мобильного приложения

**Цель.** Рабочий Compose-bootstrap по стеку [ANDROID.md](ANDROID.md), на котором строятся все экраны.

**Объём.**
- Gradle Wrapper + version catalog (`gradle/libs.versions.toml`), стабильные совместимые AGP/JDK/Kotlin/Compose compiler/KSP, Compose BOM. Без динамических версий `+`/SNAPSHOT.
- Single Activity, Material 3 (светлая/тёмная тема), edge-to-edge.
- Navigation 3 с типизированными маршрутами, сохранение back stack.
- Базовая архитектура: `UiState` (Loading/Content/Empty/Error), ViewModel + StateFlow + UDF, конструкторная инъекция.
- Каркас репозиториев (`RecipeRepository` и др. как интерфейсы), базовый HTTP-клиент (Ktor Client + kotlinx.serialization).
- Основа юнит-тестов (JUnit + kotlinx-coroutines-test, fakes) и один минимальный экран-заглушка.
- `minSdk`/`targetSdk`/`applicationId` зафиксированы в `workflow/project.md`.

**Требования к нижестоящим задачам.**
- Стабильная сборка, сетевой клиент и DI-контейнер, к которым подключаются **3–15** без пересоздания каркаса.
- Единый дизайн-токен (тема/типографика/цвета) для всех экранов.

**Критерии готовности.**
- [ ] `:app:assembleDebug` проходит без ошибок.
- [ ] Приложение запускается как single-Activity Compose, нет XML-layout/Fragment/RecyclerView.
- [ ] Navigation 3 настроен с типизированными маршрутами и хотя бы одним маршрутом.
- [ ] Material 3 тема с поддержкой светлой/тёмной темы.
- [ ] Ktor Client подключён и способен выполнить тестовый GET (к mock-серверу).
- [ ] Юнит-тестовый раннер работает (`:app:testDebugUnitTest`), есть ≥1 зелёный тест.
- [ ] `:app:lintDebug` проходит без блокирующих ошибок.
- [ ] Версии зафиксированы в version catalog; нет динамических версий.

## Задача 3 — Экран списка рецептов

**Цель.** Экран с прокручиваемым списком рецептов из mock-сервера.

**Объём.**

- Переход на деталку по тапу.

**Требования к нижестоящим задачам.**
- Навигация к деталке (**4**) с передачей `id`.
- Точка входа для добавления в избранное (**11**).
- Точка входа для фильтра/сортировки (**13**) и отображения «блюда дня» (**14**) и подборок (**15**).

**Критерии готовности.**
- [ ] Список отображает рецепты, полученные от `GET /recipes`.
- [ ] Отображаются загрузка, пустое состояние и ошибка с retry (сервер недоступен).
- [ ] Тап по карточке открывает деталку с корректным `id`.
- [ ] Состояние списка переживает поворот экрана.
- [ ] UI виден через UIAutomator/semantics (тексты — из ресурсов, не захардкожены в коде).

## Задача 8 — Запрос к DeepSeek (контекст рецепта)

**Цель.** Отправлять распознанный текст в DeepSeek и получать ответ строго в рамках выбранного рецепта/кулинарии.

**Объём.**
- Отправка текста в DeepSeek через серверный proxy (ключ не хранится в APK) — решение фиксирует `/tech`.
- System-prompt, ограничивающий ответ контекстом рецепта и кулинарии: замены ингредиентов, техника, тайминги.
- Классификация темы: если вопрос не относится к кулинарии/рецепту — вернуть «вопрос не относится к теме», не отправляя произвольный ответ.

**Блокер.** Живой вызов требует API-ключа DeepSeek. Без ключа — критерий приёмки live-интеграции остаётся BLOCKED, но не блокирует каталог/избранное. Mock/typed input не засчитывается за живую интеграцию.

**Требования к нижестоящим задачам.**
- Текст ответа как вход для TTS (**9**).
- Механизм «DeepSeek может запустить таймер» (**12**): распознавание намерения таймера (function calling/структурированный вывод) на этой стороне.

**Критерии готовности.**
- [ ] Распознанный текст уходит в DeepSeek, ответ возвращается и отображается.
- [ ] Некулинарный вопрос получает ответ «вопрос не относится к теме» (детерминированно, без утечки в произвольную тему).
- [ ] Ответ ограничен контекстом рецепта (проверено сценарием).
- [ ] Ошибка сети/таймаут DeepSeek обработана и показана пользователю.
- [ ] Live-вызов подтверждён реальным ключом; иначе критерий помечен BLOCKED.

## Задача 11 — Избранное и офлайн-просмотр

**Цель.** Добавление рецепта в избранное и его просмотр без сети.

**Критерии готовности.**

- [ ] Избранное переживает перезапуск приложения (Room-персист).
